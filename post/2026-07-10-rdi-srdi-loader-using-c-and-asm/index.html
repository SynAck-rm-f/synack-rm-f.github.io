Base Loader Manual PE Mapper

Manual PE Mapper / Reflective Loading Pipeline

The engine incorporates a custom Reflective DLL Injection (RDI) / manual mapping pipeline designed to instantiate PE payloads directly from memory without invoking the native operating system loader (LdrLoadDll / ntdll!LdrpLoadDll), completely bypassing standard user-mode loader callbacks and telemetry.

Manual Mapping Execution Sequence

  • Buffer Acquisition & Staging : Loading the raw PE binary from disk or memory storage into an unmapped temporary buffer (pRawBuffer).
  • PE Header Validation : Parsing and verifying foundational structures via IMAGE_DOS_SIGNATURE (MZ) and IMAGE_NT_SIGNATURE (PE\0\0).
  • Virtual Memory Allocation : Reserving and committing virtual memory matching SizeOfImage via VirtualAlloc with initial PAGE_EXECUTE_READWRITE permissions.
  • Section Mapping : Copying PE headers (SizeOfHeaders) and iterating through the section header array to project raw data blocks into their respective relative virtual addresses (VirtualAddress ← PointerToRawData).
  • Base Relocations Resolution : Traversing the relocation directory (IMAGE_DIRECTORY_ENTRY_BASERELOC) to apply delta adjustments (uDeltaBase = TargetBase - OptionalHeader.ImageBase) across absolute memory pointers.
  • Import Address Table (IAT) Patching : Resolving dependencies specified in IMAGE_DIRECTORY_ENTRY_IMPORT by loading required modules and patching function pointers into the IAT.
  • Entry Point Execution & Cleanup : Computing the absolute address of AddressOfEntryPoint, executing DllMain with the DLL_PROCESS_ATTACH reason code, and unmapping temporary staging buffers.

Stealth Loader Reflective Stages

Advanced Reflective Stages & Lifecycle

The reflective execution pipeline incorporates advanced staging logic initially pioneered by Stephen Fewer (2009) and extended to shellcode-based reflection (sRDI) by Adam Chester (2016). The complete operational lifecycle maps the native loader workflow entirely within user-space context:

Execution Sequence

  • Staging & Acquisition : Binary buffers are sourced from memory or disk streams, bypassing standard CreateFile monitoring if unbacked buffers are injected via remote handles.
  • PE Header Parsing : Extraction of IMAGE_NT_HEADERS, IMAGE_SECTION_HEADER, and IMAGE_DATA_DIRECTORY boundaries to determine image layout requirements.
  • Virtual Allocation & Section Projection : Reserving memory via VirtualAlloc/VirtualAllocEx and mapping raw section blocks to their respective Relative Virtual Addresses (RVA).
  • Base Relocations Application : Adjusting absolute address pointers using the computed memory delta (uDeltaBase).
  • Import Address Table (IAT) Resolution : Resolving dependencies dynamically by invoking custom LoadLibraryA/GetProcAddress equivalents.
  • Section Memory Protection Alignment : Iterating through section characteristics (IMAGE_SCN_MEM_READ, IMAGE_SCN_MEM_WRITE, IMAGE_SCN_MEM_EXECUTE) to apply strict permissions via VirtualProtect/VirtualProtectEx, avoiding persistent PAGE_EXECUTE_READWRITE (RWX) footprints across the entire mapping.
  • Thread Local Storage (TLS) Callback Execution : Enumerating IMAGE_DIRECTORY_ENTRY_TLS to execute callback routines prior to main entry execution, ensuring thread-specific initialization integrity.
  • Entry Point Invocation : Resolving AddressOfEntryPoint and executing DllMain with the DLL_PROCESS_ATTACH notification reason.

Virtual Allocation & Section Mapping

The mapping engine allocates a contiguous virtual address space matching the image requirements defined in the PE optional headers, then projects individual sections from the raw staging buffer to their respective Relative Virtual Addresses (RVAs).

  1. Virtual Memory Reservation & Allocation :
    • Attempts to allocate memory at the preferred ImageBase specified in the PE headers using VirtualAlloc with MEM_RESERVE | MEM_COMMIT and initial PAGE_EXECUTE_READWRITE permissions.
    • Implements a fallback mechanism: if the preferred address is occupied or invalid (e.g., due to ASLR conflicts), VirtualAlloc is reinvoked with a NULL base parameter to let the operating system assign an available region.
  2. Header Projection : Copies the complete PE header block (SizeOfHeaders) from the raw staging buffer directly to the base of the newly allocated memory region.
  3. Section Iteration & Mapping :
    • Locates the first section header via the IMAGE_FIRST_SECTION macro.
    • Iterates through the section array (NumberOfSections), copying raw data (PointerToRawData) into target virtual addresses (VirtualAddress) based on section sizing constraints (SizeOfRawData).

Base Relocation Table Traversal & Delta Patching

During the manual mapping execution flow (bypassing standard Windows loader routines), the payload must resolve absolute memory addresses if the allocated memory base differs from the compiled preferred image base (due to ASLR). This is handled by parsing the IMAGE_DIRECTORY_ENTRY_BASERELOC directory without relying on standard OS APIs like LdrProcessRelocationBlock.

Control Flow & Implementation:

The loader reads the base relocation directory from the NT Headers. It traverses the raw relocation table in memory by maintaining a relocationsProcessed counter. The table is composed of BASE_RELOCATION_BLOCK structures, each containing a PageAddress (RVA) and an array of BASE_RELOCATION_ENTRY structures that specify 12-bit offsets and types within that page.

A notable defensive coding practice is implemented before patching: the loader performs an explicit bounds check (relocationRVA > dwImageSize - sizeof(DWORD_PTR)) to prevent potential Access Violations (0xC0000005) if the PE file is malformed, truncated, or utilizes anti-disassembly techniques. If the RVA is valid and the type is non-zero (skipping IMAGE_REL_BASED_ABSOLUTE padding), the delta offset is applied directly to the pointer located at the calculated RVA.

Import Address Table (IAT) Resolution

Following memory mapping and relocation fixups, the loader must resolve the PE’s dependencies. This snippet iterates through the IMAGE_DIRECTORY_ENTRY_IMPORT array to map required DLLs into the process address space and resolve their exported function addresses into the IAT.

The implementation correctly handles the dual-table structure of PE imports:

  1. INT (Import Name Table / OriginalFirstThunk): Used to read the function name or ordinal.
  2. IAT (Import Address Table / FirstThunk): Overwritten in-place with the actual memory address returned by the resolver.

It also includes a fallback mechanism (if (!originalThunk) originalThunk = thunk;) to handle edge cases where a compiler/linker might null out the OriginalFirstThunk (bound imports).

Low-Level Analysis & Evasion Critique:

  • High Detection Vector: The reliance on LoadLibraryA and GetProcAddress heavily degrades the stealth of this manual mapper. These are standard, high-level Win32 APIs that are almost universally hooked by EDR/AV solutions (via userland hooking). Calling them to resolve imports for a manually mapped payload creates a direct linkage between the malicious payload and the EDR’s telemetry pipeline.
  • Expected Red Team Implementation: To achieve true stealth, a loader of this caliber should implement Dynamic API Resolution (e.g., walking the PEB -> LdrGetDllHandle -> LdrGetProcedureAddress) or resolve exports manually by parsing the Export Directory of the newly loaded DLL in memory, completely avoiding kernel32!GetProcAddress.

The final phase of the loader lifecycle involves transitioning the payload from a passive memory state to an active execution state.

The loader implements a custom Export Address Table (EAT) parser to resolve function addresses without utilizing GetProcAddress.

uint32_t crc32b(const uint8_t *str) {
    uint32_t crc = 0xFFFFFFFF;
    uint32_t byte;
    uint32_t mask;
    int i = 0x0;
    int j;

    while (str[i] != 0) {
        byte = str[i];
        crc = crc ^ byte;
        for (j = 7; j >= 0; j--) {
            mask = -1 * (crc & 1);
            crc = (crc >> 1) ^ (SEED & mask);

        i++;

PEB Walking for Module Base Resolution (x64 ASM)

To resolve NTAPIs from ntdll.dll, the loader must first obtain the base address of the module without calling GetModuleHandle. This is achieved via inline x64 assembly (MASM) walking the Process Environment Block (PEB).

The get_ntdll procedure navigates the InMemoryOrderModuleList:

  1. Accesses the TEB via the gs segment register (gs:[60h]).
  2. Retrieves the Peb->Ldr pointer (offset 0x18).
  3. Accesses the InMemoryOrderModuleList.Flink (offset 0x20). The first entry is the executable itself.
  4. Dereferences the forward link ([rax]) to reach the second entry, which is consistently ntdll.dll in Windows processes.
  5. Extracts the DllBase (offset 0x20) from the LDR_DATA_TABLE_ENTRY.

  • xor rax, rax: This sets the value of the rax register to zero, which is a common way to initialize a register before using it.
  • mov rax, gs:[60h]: This retrieves the address of the PEB from the gs segment register, which is a register used by Windows for thread-local storage. The offset 60h is the location of the PEB pointer within the TIB (Thread Information Block), which is another data structure used by Windows to store information about threads.
  • mov rax, [rax + 18h]: This retrieves the address of the Ldr (Loader) member of the PEB, which is a pointer to a linked list of loaded modules.
  • mov rax, [rax + 20h]: This retrieves the address of the first entry in the linked list, which corresponds to the main module of the process (i.e., the executable file itself).
  • mov rax, [rax]: This retrieves the base address of the main module.
  • mov rax, [rax + 20h]: This retrieves the address of the second entry in the linked list, which corresponds to ntdll.dll.
  • ret: This returns the value of rax, which now contains the base address of ntdll.dll.

To completely detach the payload’s execution flow from static imports and EDR-monitored API resolution routines, the loader implements a strict 3-phase dynamic invocation pattern. This ensures that sensitive API names and their addresses are never statically written to the binary’s .data or .rdata sections, and high-level resolvers like GetProcAddress are never called.

  1. Base Resolution: Obtain the ntdll.dll base address via the PEB-walking assembly stub, then resolve the target function’s address using the custom EAT parser and the precompiled CRC32 hash.
  2. Type Casting: Cast the raw resolved void pointer to the strictly defined function pointer typedef (e.g., NtCreateFile_t) to enforce correct parameter passing and calling conventions (__stdcall).
  3. Obfuscated Invocation: Execute the API using the locally scoped, obfuscated function pointer variable.

Static Analysis Evasion: Static triage of the final compiled artifact reveals a highly reduced attack surface. Cutr analysis confirms the .text section is strictly constrained to 0x1000 (4096 bytes), validating the successful stripping of the C Runtime Library via -nostdlib compilation flags. Payload State & Structural Anomalies: Examination of the embedded dll.h header reveals that the dll_bin array is predominantly populated with 0x00 null bytes rather than standard PE signature bytes (MZ). This indicates the sRDI shellcode is encrypted or compressed at rest, requiring an unobserved decryption routine (likely executing prior to the PE Header Parsing phase) to decode the payload into the staging buffer. Furthermore, the binary contains a non-standard .buidlid PE section. This custom section acts as a structural IOC, likely housing the encrypted payload blob or loader-specific configuration data to avoid mixing it with standard .rdata initialization.

Behavioral Signatures (Dynamic Analysis): Despite successfully bypassing static Import Address Table analysis, dynamic execution within a CAPE sandbox successfully fingerprinted the loader via behavioral monitoring and API parameter inspection. The evasion fails against modern sandboxes due to high-fidelity behavioral indicators:

  • T1129 - Shared Modules: Triggered by the invocation of LdrLoadDll. Even though the API string is obfuscated via CRC32 hashing, EDRs monitoring ntdll syscall patterns detect the manual loading of DLLs (e.g., KERNEL32.dll, USER32.dll) that were not present in the process’s original module list.

Future Work Arcticles | Research Trajectory

While the current implementation demonstrates a fully functional sRDI-based manual PE loader with msfvenom -f dll as the payload source, several evolutionary paths remain open for hardening and operational refinement.

From Manual PE Loading to Full Syscall Invocation. The current architecture successfully strips the Windows loader from the execution path, yet it still relies on resolved NT API pointers (e.g., NtProtectVirtualMemory, NtAllocateVirtualMemory) obtained via PEB walking and hash resolution. This is robust against IAT analysis, but still traverses ntdll user-mode stubs, leaving artifacts in ETW and userland hooks. The definitive next stage is migrating the loader itself to a direct/indirect syscall model, bypassing ntdll entirely and invoking the kernel via syscall instructions with manually reconstructed SystemServiceNumber indices. This would render the loader immune to userland EDR hooks and significantly complicate telemetry correlation.

Payload Architecture Reassessment. It is critical to recognize that the current pipeline (msfvenom -f dll → xxd -i → dll.h) produces a genuine PE file, not Position-Independent Code (PIC). The sRDI loader performs the full burden of the Windows loader: parsing headers, mapping sections, processing relocations, and rebuilding the Import Address Table. The payload is not position-independent — the loader makes it so at runtime. Future iterations should evaluate whether this PE-centric approach remains optimal, or whether shifting to a pure shellcode paradigm offers superior evasion against memory scanners that hunt for mapped PE headers in anomalous regions.
