Understanding payload execution at the binary level requires stripping away high-level abstractions and observing how the CPU processes raw machine code. Whether generating payloads via Metasploit (msfvenom) or compiling custom position-independent shellcode (PIC), the underlying compilation pipeline follows a deterministic path from assembly source code down to raw opcodes.

This write-up breaks down the internal mechanics of transforming x86_64 assembly into a clean, position-independent byte array, analyzing ELF object structures, relocation traps, and binary extraction workflows.

This write-up builds upon the concepts and methodology presented in Windows Shellcoding in Depth (Church of Malware).

1. Low-Level Assembly Payload Construction

Consider a minimal Linux x86_64 payload designed to execute a sys_write syscall (rax = 1) targeting stdout (rdi = 1), followed by a clean sys_exit (rax = 60).

2. Compilation and Disassembly Analysis

Assembling the source file using NASM yields an unlinked ELF object file (.o).

1

nasm -f elf64 hello.asm -o hello.o

Inspecting the disassembly via objdump exposes the underlying opcodes associated with each instruction mnemonic:

1

objdump -d hello.o

The hexadecimal column contains the raw opcodes executed by the CPU.

3. Position-Independent Code (PIC) & Relocation Hazards

Extracting opcodes directly from an object file does not guarantee functional shellcode. The primary constraint of shellcode execution is that it must be Position-Independent Code (PIC) it must execute properly regardless of the memory address where it is injected.

Analyzing relocation tables with readelf reveals potential hazards:

1

readelf -r hello.o

The Problem with Absolute Offsets and Relocations

  • If assembly references absolute memory addresses or relies on the linker (ld) to resolve symbols via relocation tables (R_X86_64_PC32), the payload will crash when executed inside an arbitrary target process context.

  • Null Bytes (\x00): Standard string-based injection vectors (e.g., buffer overflows targeting strcpy) truncate payloads containing \x00. Offsets and immediate values (like mov rax, 1) introduce null bytes into the byte stream (b8 01 00 00 00).

6. Why does objcopy -O binary work on both from objets and Executable ?

The objcopy -O binary command does one very simple thing: it strips ALL ELF headers (whether ET_REL or ET_EXEC) and extracts only the raw bytes from the code sections (mainly .text).

if: objcopy -O binary hello.o payload.bin (Direct from the object file)

  • extract the .text section before the linker has touched the addresses.
  • If code uses external symbols or poorly managed global variables, the extracted bytes will contain unresolved dummy/relative addresses (0x00000000).
  • If code is pure Position-Independent Code (PIC) — no relocations, just instruction opcodes and PC-relative offsets the extracted bytes are already perfectly valid.

if: objcopy -O binary shellcode.elf shellcode.bin (After the linker)

  • extract the .text section after the linker has done its job.
  • If code contained addresses that were resolved by ld (for example, to a fixed address like 0x401000), those hardcoded addresses (0x00 0x10 0x40 0x00) will be burned into your shellcode bytes.
  • Consequence for a shellcode: If the shellcode is injected into a third-party process at address 0x7fff12340000, it will crash as soon as it tries to jump to 0x401000.

foundation derived from the COFF (Common Object File Format)

Executable files on Unix and Windows share a common foundation derived from the COFF (Common Object File Format) specification:

  • Windows: Uses the PE (Portable Executable) format (.exe, .dll, .sys, .scr), which extends COFF for 32-bit and 64-bit binaries.
  • Linux: Uses the ELF (Executable and Linkable Format) structure.

PE (Portable Executable) is a structured data format providing the Windows OS loader (ntdll/kernel32) with the metadata required to map code into memory, resolve API import/export tables (IAT/EAT), bind dynamic libraries (DLLs), and handle Thread Local Storage (TLS).

Disk vs. Memory Layout

The PE data structures on disk mirror those loaded in virtual memory. However, the OS loader does not perform a raw 1:1 file map:

  • Selective Mapping: The loader parses the PE headers, allocating specific virtual memory sections based on the SizeOfImage field and section alignment.
  • Memory Sections: A loaded module in memory contains only the executable code, data, and resources required by the host process.
  • Unmapped Data: Non-essential structures (such as debug symbols or relocation tables when loaded at their preferred base address) are placed at the end of the PE file on disk and are either read on demand or omitted from virtual memory mapping entirely.
